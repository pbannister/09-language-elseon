# C2 vs C3

Study note for the episode 1-A lineage, per `prompts/11-c-comparison-criteria.md`.
Baseline is C, as in the episode 1-A studies; the two candidates are assessed side by side.
Scope: what C2 and C3 each tried, what worked, what did not work, and what Elseon should borrow or avoid.
Primary sources are the C2 repository and its documentation set ([c2lang/c2compiler](https://github.com/c2lang/c2compiler)), and, for C3, `documents/13-c3-vs-c.md` with its cited primary sources.
Live-state observations (repository metrics, release status, file layout) were recorded on 2026-09-16.
The official C2 site (c2lang.org) did not respond at observation time, so C2 claims are cited to the repository documentation, which is the source of that site, and to the archived site.
"Stated by the project" marks project claims; "observed" marks what was checked against primary material or public data.

The two are one lineage, not two independent candidates: C3 began as an experimental fork of C2 by Bas van den Berg, and "has evolved significantly, not just in syntax but also in regard to error handling, macros, generics and strings" ([C3 Design Goals](https://c3-lang.org/getting-started/design-goals/)).
This note therefore reads as a parent-versus-child comparison: C3's divergences are evidence about which of C2's decisions survived contact with a second designer's judgment.

## 1. Positioning

- C2 positions as an "evolution of C" ([C2 docs: Philosophy](https://github.com/c2lang/c2compiler/blob/master/docs/docs/index.md)), and the compiler man page states the target domain in C's own terms: "C2 is intended to be used in the same fields where C is currently in use. That means low-level programs like bootloaders, kernels, drivers and system-level tooling" ([c2c.1](https://github.com/c2lang/c2compiler/blob/master/c2c.1)).
- C3 positions as an "evolution of C" too, but for "general-purpose systems programming language for building native software" ([C3 Introduction](https://c3-lang.org/getting-started/introduction/)), and its author later concluded that marketing it as a "C alternative" was a mistake because that phrase means OS, embedded, and niche work ([C3 study §1](documents/13-c3-vs-c.md)).
- So the fork's decisive divergence is audience, not syntax: C2 kept C's stated domain (kernels and drivers) while C3 moved to application development.
- Both state the same core constraint set: stay close to C, be easy for a C programmer to learn, and interoperate with C ([C2 docs: Design goals](https://github.com/c2lang/c2compiler/blob/master/docs/docs/index.md), [C3 Design Goals](https://c3-lang.org/getting-started/design-goals/)).
- Both explicitly reject higher-level features: C2 lists "higher-level features (like object-orientation, garbage collection, etc.)" as a non-goal ([C2 docs: Design goals](https://github.com/c2lang/c2compiler/blob/master/docs/docs/index.md)); C3 says "avoid 'big ideas'" and rejects constructors and destructors ([C3 study §1](documents/13-c3-vs-c.md)).
- C2's differentiation claims are development speed, compilation speed, an integrated build system, and tooling ([C2 docs: Design goals](https://github.com/c2lang/c2compiler/blob/master/docs/docs/index.md)); C3's are ergonomics, safety in safe mode, and a batteries-included standard library ([C3 study §1](documents/13-c3-vs-c.md)).
- Both are single-author-led projects that outgrew their author's original framing; C2's author wrote that he re-implemented the compiler in C2 itself as "the graduation test for the C2 language as far as I am concerned" ([C2 site archive: A Year later](https://web.archive.org/web/20260105183102/http://c2lang.org/), 2023-05-24).
- Against the C baseline, both offer the same headline trade: modules instead of headers, fixed-width types, and defined behavior, in exchange for abandoning C's textual preprocessing model.
- Refinement of `documents/08-related-work.md`: the two Camp 1 rows are one lineage with one upstream and one downstream; the survey's "Smaller community" note for C2 is correct but incomplete — C2 is also the older project, the one that proved the concept before C3 re-scoped it.

## 2. Kernel-test adherence

- Both projects predate Elseon's kernel test and were not written to pass it, so each guarantee is assessed separately with evidence.

**No garbage collection / no hidden runtime.**

- C2: no GC is a stated non-goal, and allocation is the C library's own (`malloc`/`free`) reached through hand-written `libc` interface files ([C2 docs: Design goals](https://github.com/c2lang/c2compiler/blob/master/docs/docs/index.md), [C2 docs: Libraries](https://github.com/c2lang/c2compiler/blob/master/docs/docs/build_system/libraries.md)).
- C2 defaults to using libc: "usage of libc is opt-out. By default each program uses it. This is a convenience choice" ([C2 docs: Libraries](https://github.com/c2lang/c2compiler/blob/master/docs/docs/build_system/libraries.md)), so a C2 program links the platform C runtime unless told otherwise.
- C3: no GC and no hidden unwinding, but the same default dependency on the platform C runtime and an implicit standard-library import ([C3 study §2](documents/13-c3-vs-c.md)).
- Assessment: a tie at "no GC"; neither demonstrates a kernel build with no runtime beyond what a kernel accepts.

**No hidden allocations.**

- C2: allocation is a plain library call on an interface module the programmer imports and names; there are no language-level containers to allocate implicitly, and `init` calls are syntax for calling a function the source names ([C2 docs: Init calls](https://github.com/c2lang/c2compiler/blob/master/docs/docs/language/init_calls.md)).
- C3: mechanisms are explicit, but sites can be implicit — uninitialized `List`/`HashMap`/`DString` default to the temp allocator, and the compiler injects a `@pool()` scope into `main` when it sees a temp allocation ([C3 study §2](documents/13-c3-vs-c.md)).
- Assessment: C2 is closer to Elseon here, but by omission rather than by rule: C2 has no standard containers, so it never had the problem C3 created and then constrained.

**No hidden control flow.**

- C2: `init` calls are explicit syntactic sugar — `Type name.func(args)` declares the variable and then calls `Type.func(&name, args)` as a separate statement, and the docs enumerate where it is disallowed (globals, statics, conditions, `for` init-clauses) ([C2 docs: Init calls](https://github.com/c2lang/c2compiler/blob/master/docs/docs/language/init_calls.md)).
- C2 has no destructors: a repository tree search on 2026-09-16 found zero paths matching "destruct" and zero matching "defer" across 2,049 tracked entries (observed).
- C2 keeps `goto` and labels "just like in C" ([C2 docs: Flow control](https://github.com/c2lang/c2compiler/blob/master/docs/docs/language/flow_control.md)); C3 removed `goto` because it interacts badly with `defer` and optional unwrapping ([C3 study §2](documents/13-c3-vs-c.md)).
- C3: errors are explicit optionals, but safe mode inserts implicit bounds and null checks and evaluates contracts, and `assert` degrades to an LLVM unreachable hint in unchecked mode ([C3 study §2](documents/13-c3-vs-c.md)).
- Assessment: C2 wins on this dimension. Its control flow is exactly what the source shows; the only mode-dependent switch documented is `disable-asserts`, an explicit build choice ([C2 docs: Recipe file](https://github.com/c2lang/c2compiler/blob/master/docs/docs/build_system/recipe_file.md)).
- The irony worth recording: C2's honesty here is largely a consequence of having fewer safety features, not of a stronger rule; elseon's rule must hold while adding checks C2 never had.

**Deterministic memory layout.**

- C2: fixed-width primitives with no `short`/`long`/`signed`/`unsigned` spellings, plus `isize`/`usize` for pointer-sized integers ([C2 docs: Basic types](https://github.com/c2lang/c2compiler/blob/master/docs/docs/language/basic_types.md)).
- C2 adds `reg8`..`reg64`: "plain unsigned integers that are also implicitly `volatile`, for memory-mapped hardware registers" ([C2 docs: Basic types](https://github.com/c2lang/c2compiler/blob/master/docs/docs/language/basic_types.md)) — a kernel-facing convenience with no C3 equivalent.
- C2 exposes type properties as fields (`i32.max`, `char.width`, `f32.nan`) and provides `bit offsets` for explicit bit-layout control ([C2 docs: Basic types](https://github.com/c2lang/c2compiler/blob/master/docs/docs/language/basic_types.md), [C2 docs: Changes from C](https://github.com/c2lang/c2compiler/blob/master/docs/docs/introduction/changes_from_c.md)).
- C3 matches on fixed widths, wraps signed overflow, forbids implicit narrowing, defines evaluation order, and controls layout with `@packed`/`@align`/`bitstruct` ([C3 study §2](documents/13-c3-vs-c.md)).
- Both keep C's struct-layout rules by default, which is what preserves ABI compatibility; neither documents automatic field reordering.
- Assessment: a tie on determinism; C2 is slightly stronger for kernel work because `reg*` and bit offsets are built for hardware, while C3's safe-mode checks add representation-adjacent behavior C2 lacks.

**C compatibility (Elseon's fourth kernel-test element).**

- C2: "Easy integration with C libraries" is a stated design goal, and the man page claims the same domains as C ([C2 docs: Design goals](https://github.com/c2lang/c2compiler/blob/master/docs/docs/index.md), [c2c.1](https://github.com/c2lang/c2compiler/blob/master/c2c.1)).
- C2 keeps the qualifiers that carry ABI and semantics: `const` and `volatile` are C2 keywords, and `extern` (with `int`, `long`, `short`, `signed`, `unsigned`, `typedef` and others) is usable in interface files with its C semantics ([C2 docs: Keywords](https://github.com/c2lang/c2compiler/blob/master/docs/docs/language/keywords.md)).
- C2 reserves `restrict`, `do`, `register`, and other C keywords "to avoid compatibility problems" rather than adopting them as C2 features ([C2 docs: Keywords](https://github.com/c2lang/c2compiler/blob/master/docs/docs/language/keywords.md)).
- C3 removed `const`, `volatile`, and `restrict`, and replaced volatile with `@volatile_load`/`@volatile_store` macros ([C3 study §3](documents/13-c3-vs-c.md)).
- Assessment: C2 is materially closer to C's type surface, which matters directly to Elseon's PFE goal of ingesting real C headers without losing qualifier meaning.

## 3. Syntax family

- C2 keeps C's statement shape: the documentation's own summary is that code "inside function bodies is almost identical to C, while code outside function bodies differs a bit more" ([C2 docs: Code fragments](https://github.com/c2lang/c2compiler/blob/master/docs/docs/introduction/code_fragments.md)).
- C2 removes `do`..`while` ("error-prone ... its main real-world use — expanding to a single statement inside a macro — doesn't apply in a language without macros") and removes header files and forward declarations ([C2 docs: Changes from C](https://github.com/c2lang/c2compiler/blob/master/docs/docs/introduction/changes_from_c.md)).
- C2 unifies type definition syntax under `type <name> <definition>` for enums, structs, unions, functions, and aliases ([C2 docs: User-defined types](https://github.com/c2lang/c2compiler/blob/master/docs/docs/language/user_types.md)).
- C2 makes member access always `.`, never `->`, and requires `fn` on functions, as C3 does ([C2 docs: Changes from C](https://github.com/c2lang/c2compiler/blob/master/docs/docs/introduction/changes_from_c.md), [C3 study §3](documents/13-c3-vs-c.md)).
- C2 enforces identifier case as a compile error: types, enum constants, and global constants must start uppercase; modules, functions, variables, and members must start lowercase ([C2 docs: Naming](https://github.com/c2lang/c2compiler/blob/master/docs/docs/language/naming.md)).
- C3 enforces a comparable but different rule (types PascalCase, values lower-case) for the same stated reason: one token of lookahead ([C3 study §3](documents/13-c3-vs-c.md)).
- C2 scopes enum constants through the type (`State.Begin`), which shortens names and avoids the `STATE_BEGIN` convention ([C2 docs: User-defined types](https://github.com/c2lang/c2compiler/blob/master/docs/docs/language/user_types.md)).
- C2 adds string switches, multi-condition cases, `init` lists, raw strings, and auto-arguments that fill `file`/`line`/`func` without macros ([C2 docs: Changes from C](https://github.com/c2lang/c2compiler/blob/master/docs/docs/introduction/changes_from_c.md), [C2 docs: Attributes](https://github.com/c2lang/c2compiler/blob/master/docs/docs/language/attributes.md)).
- C2 deliberately keeps conditional compilation: `#if`, `#ifdef`, `#ifndef`, `#elif`, `#else`, `#endif` are keywords ([C2 docs: Keywords](https://github.com/c2lang/c2compiler/blob/master/docs/docs/language/keywords.md)).
- C3 removed the `#` preprocessor and replaced user macros with a typed semantic macro system ([C3 study §3](documents/13-c3-vs-c.md)).
- This is a real fork in the road for Elseon: C2 shows that a header-less language can still keep feature selection; C3 shows that a language can eliminate preprocessing entirely but pays with a macro system of its own.
- Surface choices Elseon would likely reject from both: the mandatory case grammar (both projects) trades C identifier freedom for parseability with no kernel-test benefit, and C3's mode-dependent semantics remain the sharper problem.
- C2's `reg*` types and bit offsets are syntax-family additions Elseon should study directly: they encode hardware intent in the type rather than in a comment or a cast.

## 4. C interoperability

- C2's distinguishing feature is that it makes a library a language-level concept rather than a pair of loose steps: "In C2, the compiler does have a concept of library. So using a library is more of an atomic action; either you use it or not" ([C2 docs: Libraries](https://github.com/c2lang/c2compiler/blob/master/docs/docs/build_system/libraries.md)).
- C2 maps C headers to modules through a manifest: "Since C2 doesn't use `#include` headers, a new mechanism is required to map C header files to C2 modules. This is the purpose of a *manifest* file" ([C2 docs: Libraries](https://github.com/c2lang/c2compiler/blob/master/docs/docs/build_system/libraries.md)).
- In practice the mapping is hand-authored: the shipped `c2libs/` tree contains per-header interface files such as `libc/stdio.c2i`, `libc/stdlib.c2i`, `math/math.c2i`, and `pthread/pthread.c2i`, each library carrying a `manifest.yaml` ([C2 docs: Libraries](https://github.com/c2lang/c2compiler/blob/master/docs/docs/build_system/libraries.md)).
- The compiler can generate interface files — "When c2c generates an *interface file* (eg. module.c2i), it will only generate: ..." ([C2 docs: Attributes](https://github.com/c2lang/c2compiler/blob/master/docs/docs/language/attributes.md)) — but the compiler consumes `.c2i` interfaces, not C headers directly.
- C2's `.c2i` files must still declare the C functions themselves with `extern`; the interfaces are C2 source, so this is a curated binding layer rather than header ingestion.
- No name checks are performed on external libraries or `.c2i` files, which is the escape hatch that lets C's naming survive inside a case-enforcing language ([C2 docs: Naming](https://github.com/c2lang/c2compiler/blob/master/docs/docs/language/naming.md)).
- C3 by contrast has full C ABI compatibility with demonstrated mixed C/C3 builds (vkQuake) and `c-sources` project support, but interop is hand-written `extern` re-declaration with a documented gotcha list, and its C-to-C3 converter remains a help-wanted item ([C3 study §4](documents/13-c3-vs-c.md)).
- C2's `$backend c` mode goes further than C3 in one respect: c2c can emit portable C, which means a C2 target can be handed to any existing C compiler or cross-compiler ([C2 docs: Evolution](https://github.com/c2lang/c2compiler/blob/master/docs/docs/introduction/evolution.md)).
- Assessment against Elseon's PFE: neither candidate ingests C headers as first-class semantic modules, so both leave Elseon's differentiator open; C2 is the better model for the *packaging* half (one library, one manifest, one declaration of intent) and C3 is the better model for the *ABI* half (proven mixed-build linking).
- The synthesis's finding stands and is now sharper: the nearest approach to PFE in the whole study series is still a hand-maintained binding layer, which is exactly the labor Elseon intends to remove.

## 5. Toolchain

- C2 is self-hosting: "Since 2024, c2c has been written in C2 itself," built by a small C bootstrap compiler ([C2 docs: The C2 compiler](https://github.com/c2lang/c2compiler/blob/master/docs/docs/introduction/the_c2_compiler.md)).
- C2's compiler is about 250 files and 57,000 lines of C2, and the project reports parse and analysis of its own source in roughly 11.7 ms and 6.8 ms on an Apple M4 ([C2 docs: The C2 compiler](https://github.com/c2lang/c2compiler/blob/master/docs/docs/introduction/the_c2_compiler.md)).
- C2 supports two backends selected per target in the recipe: `$backend c` (default) transpiles to portable C for a system compiler, and `$backend ir` generates machine code through the compiler's own SSA-based IR and register allocator for amd64, arm64, and riscv64 ([C2 docs: Evolution](https://github.com/c2lang/c2compiler/blob/master/docs/docs/introduction/evolution.md)).
- C2's IR backend is early: the project's own status table rates it "20% — Generating IR, some optimizations, no lowering yet," with embedded support at 10% and `C2Format` at 0% ([C2 docs: Current status](https://github.com/c2lang/c2compiler/blob/master/docs/docs/development/current_status.md)).
- The IR backend reached its first assembly output on 2025-11-16 (RV64), and the project states it "cannot self-compile c2c yet" ([C2 site archive](https://web.archive.org/web/20260105183102/http://c2lang.org/), [C2 docs: Current status](https://github.com/c2lang/c2compiler/blob/master/docs/docs/development/current_status.md)).
- C2 has no LLVM dependency at all: a tree search on 2026-09-16 found zero paths matching "llvm" or "qbe" among 2,049 tracked entries (observed), after the original C++/Clang-based compiler was replaced.
- That replacement is measurable: the original C++ compiler was 6.9 MB "since it used some Clang components and statically linked LLVM," while the C2-native compiler is 200 KB with comparable front-end functionality ([C2 site archive: The next step](https://web.archive.org/web/20260105183102/http://c2lang.org/), 2022-11-13).
- C3 goes the other way: LLVM 19–24 with default 23, codegen taking over 98% of unoptimized compile time, per the author's own measurement ([C3 study §5](documents/13-c3-vs-c.md)).
- C2's build system is integrated and mandatory — a project requires a `recipe.txt`, with an optional `build.yaml` for cross-compilation, library paths, and the C backend's compiler and flags ([C2 docs: Build system](https://github.com/c2lang/c2compiler/blob/master/docs/docs/build_system/intro.md), [C2 docs: Build file](https://github.com/c2lang/c2compiler/blob/master/docs/docs/build_system/build_file.md)).
- C2's build file is explicitly designed for third-party build systems: it can be "generated by a 3rd party build system like Yocto/Buildroot," and the recipe/build split assigns the recipe to developers and the build file to builders ([C2 docs: Build system](https://github.com/c2lang/c2compiler/blob/master/docs/docs/build_system/intro.md), [C2 site archive: Library management](https://web.archive.org/web/20260105183102/http://c2lang.org/), 2020-02-14).
- C2 has a plugin system that loads during compilation and can modify the AST, with shipped plugins for dependencies, cross-references, unit tests, file loading, and shell commands ([C2 README](https://github.com/c2lang/c2compiler/blob/master/README.md), [C2 docs: Current status](https://github.com/c2lang/c2compiler/blob/master/docs/docs/development/current_status.md)).
- C2's supported targets are Linux x86_64, Darwin x86_64/arm64, FreeBSD amd64, and OpenBSD amd64; embedded image generation is 10% complete ([C2 docs: Current status](https://github.com/c2lang/c2compiler/blob/master/docs/docs/development/current_status.md)).
- C3 has more targets declared, including freestanding ELF and MCU rows, but those rows are marked untested and WASM has no CI ([C3 study §5](documents/13-c3-vs-c.md)).
- Debugging: C3 documents safe-mode backtraces, sanitizers, and tracking allocators, with a long debug-info issue trail for gdb/lldb stepping ([C3 study §5](documents/13-c3-vs-c.md)); C2 documents no comparable debug-info story (unverified rather than absent).
- Maturity: C3 ships dated releases on a monthly-to-quarterly cadence and was at v0.8.4 on 2026-09-11 ([c3c releases](https://github.com/c3lang/c3c/releases)); C2 has published no GitHub releases, and the project describes itself as usable for real projects only with the C backend ([C2 docs: Current status](https://github.com/c2lang/c2compiler/blob/master/docs/docs/development/current_status.md)).
- Kernel-adjacent constraint: C2's stated purpose is kernels and bootloaders and it keeps opt-in libc and inline assembly, while C3's freestanding story is untested; neither ships a kernel build flow, so neither discharges the constraint (both marked unverified).
- Relevance to Elseon's backend choice: C2 is the one data point in the whole study series that abandoned LLVM after using it and reports a dramatic size and speed improvement, which does not refute Elseon's LLVM plan but does date it — the alternative is a multi-year backend project, as C2's 20% IR status shows.

## 6. Ecosystem and adoption

- Repository age: C2 was created 2013-01-12 and C3 on 2019-07-31, so C2 has roughly six years' head start (observed via repository metadata, 2026-09-16).
- Scale: C2 has ~837 stars and ~56 forks; C3 has ~5,819 stars and ~403 forks (observed, 2026-09-16).
- Activity: both are actively pushed — C2 on 2026-09-11 and C3 on 2026-09-17 — so the smaller community is not an abandoned one (observed).
- License: C2 is Apache-2.0 ([c2lang/c2compiler](https://github.com/c2lang/c2compiler)); C3 is dual MIT (everything but `src/`) with LGPL 3.0 for the compiler source ([C3 study §6](documents/13-c3-vs-c.md)).
- Release artifacts: C3 publishes tagged releases (v0.8.4 on 2026-09-11) with prereleases; C2 publishes none, so users build from source through the bootstrap ([c3c releases](https://github.com/c3lang/c3c/releases), [C2 README](https://github.com/c2lang/c2compiler/blob/master/README.md)).
- C2's flagship evidence of self-use is the compiler itself, plus a ported Vulkan example: "The Vulkan API comes with a header of some 3775 lines of C code" and the port produced the `c2libs/vulkan` binding ([C2 site archive: Vulkan example](https://web.archive.org/web/20260105183102/http://c2lang.org/), 2017-01-02).
- C2's own framing of its practical use is the milestone post "Since working on the custom IR backend, one milestone was to fully translate a (simple) program into assembly" (2025-11-16), with self-compilation still ahead — a candid statement of where the project actually is ([C2 site archive](https://web.archive.org/web/20260105183102/http://c2lang.org/)).
- C3 has a broader community surface: Discord, editor plugins, a playground, TypeScript-style bindings repositories, and a showcase including emulators, games, a UEFI library, and a flagship microkernel ([C3 study §6](documents/13-c3-vs-c.md)).
- Neither has a real package manager: C2 has the recipe/manifest library system and C3 has none by choice ([C2 docs: Libraries](https://github.com/c2lang/c2compiler/blob/master/docs/docs/build_system/libraries.md), [C3 study §6](documents/13-c3-vs-c.md)).
- Kernel-adjacent use: C2 was *designed* for the domain but documents no deployed kernel; C3 has a hobby microkernel in its showcase; both remain unverified for real kernel or production use.
- The adoption asymmetry is the main finding: the fork that re-scoped toward applications (C3) drew roughly seven times the attention of the project that kept C's stated domain (C2), which is evidence about where C-adjacent developers actually are.

## 7. What worked

- Modules instead of headers, proven in two independent implementations: C2 organizes code by module with file-scoped imports and no forward declarations, and C3 runs its whole standard library the same way ([C2 docs: Modules](https://github.com/c2lang/c2compiler/blob/master/docs/docs/language/modules.md), [C3 study §7](documents/13-c3-vs-c.md)).
- A strict, uniform declaration syntax: C2's `type <name> <definition>` unifies enums, structs, unions, aliases, and function types, and its naming rule is enforced by the compiler rather than by a linter ([C2 docs: User-defined types](https://github.com/c2lang/c2compiler/blob/master/docs/docs/language/user_types.md), [C2 docs: Naming](https://github.com/c2lang/c2compiler/blob/master/docs/docs/language/naming.md)).
- Fair development speed: C2 reports parsing 3–5 million lines per second and analysis faster than parsing, which it uses to justify type-while-you-edit tooling ([C2 docs: The C2 compiler](https://github.com/c2lang/c2compiler/blob/master/docs/docs/introduction/the_c2_compiler.md)).
- Integrated build system with a developer/builder split: the recipe belongs to developers, the build file to builders, which lets Yocto/Buildroot generate the latter ([C2 site archive: Library management](https://web.archive.org/web/20260105183102/http://c2lang.org/), 2020-02-14).
- Library use as one atomic act with a manifest, fixing C's "forget the linker flag, get an undefined reference" failure mode ([C2 docs: Libraries](https://github.com/c2lang/c2compiler/blob/master/docs/docs/build_system/libraries.md)).
- Compiler plugins that can modify the AST, shipped with dependency and cross-reference generators — tooling integrated into the compiler rather than bolted on ([C2 README](https://github.com/c2lang/c2compiler/blob/master/README.md)).
- Keeping `const` and `volatile` while dropping headers: C2 shows a header-less language can still carry C's qualifier semantics, which C3's removal of them gave up ([C2 docs: Keywords](https://github.com/c2lang/c2compiler/blob/master/docs/docs/language/keywords.md), [C3 study §8](documents/13-c3-vs-c.md)).
- Hardware-shaped types: `reg8`..`reg64` for memory-mapped registers and bit offsets for explicit bit layout are small, kernel-relevant additions that neither C nor C3 offers ([C2 docs: Basic types](https://github.com/c2lang/c2compiler/blob/master/docs/docs/language/basic_types.md), [C2 docs: Changes from C](https://github.com/c2lang/c2compiler/blob/master/docs/docs/introduction/changes_from_c.md)).
- Auto-arguments replacing `__FILE__`/`__LINE__`/`__func__`: a typed, checkable replacement for the most common macro use, and one C3 lacks ([C2 docs: Attributes](https://github.com/c2lang/c2compiler/blob/master/docs/docs/language/attributes.md)).
- Conservative evolution as a stability strategy: C2's status page claims "no major changes are expected" since it is an evolution of C ([C2 docs: Current status](https://github.com/c2lang/c2compiler/blob/master/docs/docs/development/current_status.md)), and it did not accumulate C3's churn.
- Self-hosting as the graduation test: writing the compiler in its own language proved the language usable at scale for C2 before it had users ([C2 site archive: A Year later](https://web.archive.org/web/20260105183102/http://c2lang.org/), 2023-05-24).
- Dropping LLVM is survivable: C2 went from a 6.9 MB static-LLVM C++ compiler to a 200 KB self-hosted compiler, showing a header-less C-like front end does not require LLVM for the front-end work ([C2 site archive: The next step](https://web.archive.org/web/20260105183102/http://c2lang.org/), 2022-11-13).

## 8. What did not work

- Domain conservatism did not win adoption: C2 kept C's stated audience of kernels, bootloaders, and drivers, and drew roughly one-seventh of C3's repository attention while starting six years earlier (observed, 2026-09-16).
- No releases is a distribution failure: a nine-year-old project with no published releases asks every user to bootstrap from source ([C2 README](https://github.com/c2lang/c2compiler/blob/master/README.md)).
- The custom backend is a long road: by 2025 the project reported that "work has started on a custom back-end," and in 2026 it rated that backend 20% with self-compilation still unreachable, against a working C backend ([C2 site archive: 2025 and beyond](https://web.archive.org/web/20260105183102/http://c2lang.org/), 2025-04-24; [C2 docs: Current status](https://github.com/c2lang/c2compiler/blob/master/docs/docs/development/current_status.md)).
- Embedded support was promised but is not there: 10% for image generation, with no documented bootloader or kernel built by the stock toolchain.
- Hand-maintained `.c2i` bindings do not scale to C's ecosystem: the model requires a curated interface and manifest per library, which is the same manual labor C3 suffers, merely better organized ([C2 docs: Libraries](https://github.com/c2lang/c2compiler/blob/master/docs/docs/build_system/libraries.md)).
- Keeping conditional compilation means keeping a second language inside the language: C2 preserves `#if`/`#ifdef` as keywords, so it retains the preprocessor's tooling problems without the preprocessor's macro power ([C2 docs: Keywords](https://github.com/c2lang/c2compiler/blob/master/docs/docs/language/keywords.md)).
- Documentation drift: the project's own docs state that "the exact format [of the recipe file] is still in progress," and the official site was unreachable at observation time; three of the four status rows in the docs folder are stale relative to the archive posts (observed, 2026-09-16).
- C3's counter-lessons are the mirror image of C2's conservatism, not a refutation of it: re-scoping to applications won attention but produced a decade-long 0.x churn, a signed-size reversal after five years, and a marketing post-mortem ([C3 study §8](documents/13-c3-vs-c.md)).
- Both projects show the same gap: full ABI compatibility without C-header ingestion leaves the most expensive integration work to users, which is exactly Elseon's PFE target (both marked, sources above).
- Neither project settled its core quickly: C2 has no 1.0 and no releases after thirteen years, and C3 targets 1.0 in 2028 after nine; the two ends of the "evolve slowly" to "break every 0.x" spectrum both cost users ([C2 docs: Current status](https://github.com/c2lang/c2compiler/blob/master/docs/docs/development/current_status.md), [C3 study §9](documents/13-c3-vs-c.md)).

## 9. Verdict for Elseon

- Classification: both are idea sources, not models; C2 is the minor of the two, and the pair should be read as one lineage entry in `documents/08-related-work.md`.
- `documents/08-related-work.md` classifies C2 as Camp 1 "Cleaner C: removes the preprocessor in favor of modules and imports; LLVM-based" with the note "Smaller community"; this study refines it: the preprocessor claim is wrong (C2 keeps `#if`-family conditional compilation), "LLVM-based" is obsolete (C2 removed LLVM entirely), and "smaller community" understates the adoption gap.
- C2 is not a model because it lacks C-header ingestion, has no releases, keeps conditional compilation, and has an unfinished backend; but it is a model for a narrow set of decisions Elseon should not lose.
- C3 is not a model for the reasons already recorded in `documents/13-c3-vs-c.md` (mode-dependent checks, implicit container allocation, qualifier removal), and the parent-versus-child comparison strengthens rather than weakens that verdict, because C2 kept the qualifiers C3 removed.
- The most useful reading of the pair is as a controlled experiment: same designer, same "evolution of C" premise, different audience and different degree of change, and the audience choice, not the technical one, decided adoption.

Borrow list (from C2 specifically):

- Keep `const` and `volatile` as first-class qualifiers — C2 proves a header-less C evolution can retain them, and PFE header ingestion needs their meaning.
- Type-level hardware intent: `reg*`-style volatile register types and explicit bit offsets — kernel code spells its hardware access in the type system.
- Auto-arguments for `file`/`line`/`func` — a typed, macro-free replacement for C's most common macro idiom.
- A library as one atomic declaration with a manifest — removes C's split header/linker failure mode and gives the compiler the full dependency picture.
- Integrated plugin system with bundled dependency and cross-reference generators — tooling lives in the compiler, not beside it.
- Strict, compiler-enforced naming with an external-interface escape hatch — cheap consistency if a `.c2i`-style exemption is granted to ingested headers.
- Recipe (developer intent) versus build file (builder environment) separation — maps cleanly onto a kernel build where the environment is not the developer's.
- Self-hosting as the graduation test — a concrete maturity bar for Elseon's own compiler.
- Conservative semantics with an explicit assertion switch (`disable-asserts`) instead of mode-dependent meaning — the honest version of the safety/performance tradeoff C3 got wrong.

Avoid list (from C2 specifically):

- Preparing C bindings by hand, however well packaged — it is the manual labor PFE exists to eliminate; C2's manifest model is worth copying, its hand-written `.c2i` corpus is not.
- Keeping `#if`-family conditional compilation — it preserves the preprocessor's tooling costs; elseon should make feature selection a module-level, analyzable construct.
- Shipping no releases for a decade — tag and publish artifacts from the first usable version.
- Starting a second backend before the first is finished — C2's 20% IR backend is a four-year detour beside a working C backend.
- Declaring kernel/bootloader domains without a built kernel or bootloader to show — the same overreach lesson the synthesis drew from C3's untested platforms.
- Position-by-domain without evidence that the domain's developers are moving — C2 chose the right technical domain and still lost the audience to a fork that chose a larger one.
